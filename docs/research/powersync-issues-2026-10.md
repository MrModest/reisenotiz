# PowerSync GitHub issue survey: risk for a small offline-first React 19 PWA

Date: 2026-10-20

## Scope

Open issues, plus issues closed in 2026, of `powersync-ja/powersync-js` (packages web, react, common/shared-internals, wa-sqlite), `powersync-ja/powersync-service` and `powersync-ja/powersync-sqlite-core`. Target stack: web only, `@powersync/web` 2.5.x, `@powersync/react`, self-hosted `powersync-service` with Postgres source and Postgres bucket storage.

## Method

`gh issue list` for all open issues (35 / 18 / 3) and for issues closed since 2026-01-01 (62 for powersync-js, 26 for powersync-service, 12 for powersync-sqlite-core). Bodies and comments read for every issue listed below; the rest were triaged by title (React Native, Tauri, Capacitor-only, attachments, docs, feature requests were skipped unless they touch the web SDK). Responsiveness is computed from issues created since 2026-06-01 (comment `authorAssociation` of CONTRIBUTOR/COLLABORATOR/MEMBER). Not covered: GitHub Discussions, Discord, PowerSync Cloud-only incidents.

## Summary

- Open issues: powersync-js 35, powersync-service 18, powersync-sqlite-core 3 (one is a release checklist). Only 4 powersync-js issues carry any label and none carry `bug`, so "bug count" must be judged by content: roughly 14 of the 35 open JS issues are real web/common bugs, the rest are RN/Tauri/Capacitor, attachments, drizzle/kysely, docs and feature requests. In the service, about 8 of 18 are bugs.
- Maintainers are fast: median time to first maintainer reply on 2026 issues is about 0.5 h (JS, n=14), 4.5 h (service, n=15); p90 about 3 days. Bug reports with a good repro often get a fix PR within 1-3 days (e.g. #954, #1058, service#718, service#813). Open issues with no reply are mostly the ones filed in the last weeks, or old Q&A threads.
- Release churn is high: the web SDK went 1.38 to 2.5 in about 3 months, shared-internals was split out, wa-sqlite 1.x to 2.x, and sqlite-core migration 14 deliberately breaks older SDKs. Several 2026 regressions came from this (#1050, #1058, #1056, #1119, #1125). Most were fixed within days.
- No open issue describes silent loss of `ps_crud` or local rows in the web SDK. The one actual data-destroying report is #1144 (`PRAGMA rekey` on OPFS with the encryption build; only relevant if you use encryption).
- Biggest open risks for a web PWA: OPFSCoopSyncVFS stability on Safari/iOS and multi-tab (#785, #808, #1130), an unexplained iOS 26.2 page-kill report (#1081), a stuck stream after long iOS backgrounding (#1077), and an unexplained 30 s read stall after connect on the IndexedDB VFS (#1114).
- Postgres bucket storage is the less-optimised backend: maintainers say MongoDB storage is more optimised and Postgres storage is due a structural overhaul (service#613). 2026 Postgres-storage bugs were found and fixed quickly (#718, #813, #729, #400), but #840 (large row) is open and #328 (connection count) is open. Fine for a small app, with eyes open.
- Using the IndexedDB VFS (default) with `enableMultiTabs` off, or OPFS with multi-tab off, avoids most of the open web-specific issues; the main cost is IDB VFS write speed and #1114-style stalls.

## Verdict for this app

PowerSync's web SDK on Postgres is usable, and the maintainers are unusually responsive: first reply typically within hours and fixes shipped in days. The 2026 record contains no unfixed report of silent loss of queued writes in the web SDK; the queue-related incidents (#954, #1058, #1050) were fixed within 1-7 days or were version-mismatch user errors that now have a guard. The risk is not data loss but runtime stability in browsers. OPFSCoopSyncVFS is the weak point: three open issues (#785, #808, #1130) cover multi-tab deadlocks, WebKit lock leaks that survive until the browser is quit, a Chromium renderer crash, and write slowdown from the shared-worker connection choice. Since iOS is a first-class target for a PWA, plan on the default IDBBatchAtomicVFS (single connection shared by tabs, no OPFS lock bugs), accept its slower writes, and measure it on a realistic dataset because #1114 reports a 30 s read stall after connect on that VFS with 6.4k rows (unresolved, unconfirmed by maintainers). Also unresolved: #1081 (iOS 26.2 page kills, single reporter) and #1077 (stream wedged after long iOS background, workaround: disconnect then connect on foreground). Before committing, run a spike on the actual iOS versions you support, covering cold start offline, long-lock resume, and two tabs. On the server side Postgres bucket storage works but is the second-class backend: the 2026 bugs (#718 LISTEN connection drop, #813 duplicate ops) were fixed fast, #840 and #700 are open, and maintainers openly say Mongo storage is better optimised. For a small app the performance gaps do not matter; keep rows small, pin service >= 1.27.0, add a replication-lag watchdog, and do not set aggressive idle timeouts on the storage role. Pin `@powersync/web`, `@powersync/common`, shared-internals and wa-sqlite versions together in the lockfile (the 2026 regressions mostly came from version skew and the fast 1.x to 2.x transition), avoid encryption on OPFS (#1144) and long db filenames (#1052), and treat `disconnectAndClear()` plus held stream subscriptions as needing manual re-subscription (#1121).
